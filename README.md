# Choosing Between Lidocaine and Prilocaine-Containing Anaesthesia for Laceration Repair

An interactive, referenced walkthrough of the algorithm for choosing between
lidocaine and prilocaine-containing local anaesthesia for laceration
repair — a contraindication screen for prilocaine, a time/wound-suitability
gate for the needle-free eutectic cream, a dedicated note on intravenous
regional anaesthesia for extensive hand/forearm injuries, and the
methaemoglobinaemia/LAST monitoring that follows either route. Every box
and decision point can be selected to reveal, in one place: what the step
means, why the review calls for it, and the sources behind it.

**Live site:** https://satbuhan.github.io/lidocaine-prilocaine-protocol/

**Authors:** Dr. Özgür Karcıoğlu & Dr. Satuk Buğra Han Bozatlı

## Why this exists

A flowchart alone tells a reader *what* to do at each step but not *why*,
and a reader outside the authors' own team cannot easily check the
evidence behind a specific branch point (the 45–60 minute cut-off, the
"(safe in digits)" aside, the SpO2≈85% figure). This page keeps the
original algorithm exactly as authored, and attaches the clinical
reasoning and literature to each box without cluttering the diagram
itself.

Unlike this atlas's two no-manuscript tools (`obesity-critical-care-protocol`,
`dapagliflozin-overdose-protocol`), this tool had the best possible source
material: a complete systematic review manuscript — "Lidocaine versus
prilocaine-containing local anesthesia for laceration repair: a systematic
review with GRADE and minimal clinically important difference appraisal"
— whose own Figure 3 *is* this algorithm, and whose "Implications for
practice" paragraph explicitly maps each recommendation to numbered
references in its own 68-item bibliography. That made sourcing faster and
more reliable than the no-manuscript tools, but it did **not** mean taking
the manuscript's own citations on faith: every reference below was
independently re-resolved against its DOI, and several of the manuscript's
own characterizations turned out to be slightly optimistic on closer
reading of the underlying papers (see "Status").

## Status

This is a working version, built to be tested on both desktop and mobile.
29 references back 13 boxes. Independent re-verification of every citation
(three parallel research passes against each DOI, not the manuscript's
word alone) caught several places where the manuscript's own framing was
a little stronger than the underlying paper actually supports — these were
corrected rather than passed through, with the honest version now in both
the node text and the reference's `kind` field:

- A Cochrane review cited for "adrenaline/epinephrine is **safe** in
  digital blocks" in fact found the trial evidence too sparse to confirm
  *or* refute harm — it disproves the old absolute contraindication more
  than it proves safety. The authored box still says "(safe in digits)"
  (that text is the algorithm itself, left untouched), but the citation
  backing it is now described honestly.
- A trial cited for "prilocaine's wider systemic safety margin" in
  intravenous regional anaesthesia actually compares prilocaine with
  *ropivacaine*, not lidocaine — the real basis for that recommendation is
  a separate Bier-block complication review, now cited as the primary
  source with the first paper kept only as supporting context.
- Two studies cited for "LET gel is preferred for small facial/scalp
  wounds in children" support LET's advantage in children generally
  (more reliably achieving adequate anaesthesia without a top-up
  injection) but neither isolates facial/scalp wounds specifically — the
  facial/scalp narrowing is the review's own clinical synthesis, which is
  preserved but now flagged `needsAuthor: true` rather than presented as
  directly proven.
- A dental Cochrane review's "123 trials" framing is accurate for the
  review's overall scope, but the specific risk-ratio figure cited from it
  comes from a pooled analysis of only 2 of those 123 trials — now stated
  explicitly.

Four boxes carry a `needsAuthor: true` flag because a specific detail
could not be fully verified:

- **Contraindication-screening box** — the infant/pregnancy/oxidising-drug
  criteria are solidly sourced; G6PD deficiency is included because it is
  a relative *contraindication to the methylene blue antidote* (confirmed
  in the same source), not because that source shows G6PD deficiency
  itself worsens prilocaine toxicity, and the anaemia/cardiopulmonary
  criterion rests on a more general source that doesn't name either
  condition individually.
- **"Avoid prilocaine" box** — see the LET/facial-scalp point above.
- **Wound-edge testing decision** — a bedside verification step with no
  specific study behind the technique itself.
- **Monitoring box** — the SpO2≈85% figure traces to a real, classic
  study, but it is a canine experimental model extrapolated to the human
  teaching point, not a human clinical measurement.

See the `kind` field on each reference in `assets/content.js` for the full
detail behind every one of these.

### Two rendering bugs caught and fixed during this build

Neither is specific to this tool's content — both are fixes to the shared
`style.css`/`app.js` engine this atlas reuses, and are worth knowing about
when building the next tool:

1. **Decision-hexagon text clipping.** `.node--decision`'s clip-path
   tapered to full width over the first 25% of the box's height. A
   decision with a long title (3 lines) made the box tall enough that its
   first line started rendering *before* the taper finished, clipping the
   first letter against the hexagon's point. Fixed by taper­ing faster
   (15% instead of 25%) and widening the box slightly — see `style.css`.
2. **Edge lines drawing in front of node text instead of behind.** The
   `.node` buttons are CSS grid items with no explicit `position`/`z-index`
   (`all: unset` clears both), so they didn't reliably stack above the
   `.edges` SVG (which has explicit `z-index: 0`) the way plain DOM order
   would suggest. On a long edge that geometrically crosses several
   intervening rows, this meant the line visibly cut across other boxes'
   text instead of hiding behind them. Fixed by giving `.node` an explicit
   `position: relative; z-index: 1;`. A related issue — the new `.node--note`
   dashed-aside style used `background: transparent`, so even once edges
   sat behind nodes correctly, a passing line would still show through
   that specific box — fixed by making it opaque (`var(--paper)`) like
   every other node type.

## Disclaimer

This is an academic / educational reference tool, not a substitute for
institutional protocol or bedside clinical judgement. Verify any threshold
or management step against current local protocol before clinical use.

## How it's built

Plain HTML/CSS/JS, no build step and no framework — a single static site
that GitHub Pages can serve directly.

```
index.html          page structure
assets/style.css     design — same paper/ink/navy "journal" aesthetic as
                      the other tools, the standard branching-flowchart
                      3-column grid
assets/content.js     ← single source of truth for every node's text and
                      reference list. Edit this file to change what the
                      page says.
assets/app.js         rendering + interaction (builds the diagram and the
                      connector lines from content.js, handles the
                      click-to-expand panel on desktop and the bottom
                      sheet on mobile)
```

### Running it locally

No install needed:

```bash
python3 -m http.server 8000
# open http://localhost:8000
```

### Editing content

Open `assets/content.js`. Each entry in `NODES` is one box or decision
hexagon from the algorithm (`meaning`, `rationale`, optional `cautions`,
and `refs` pointing at numbered entries in `REFERENCES`). Add or edit a
reference in `REFERENCES` and point to it by `id` from any node. Never
change a node's `label` or `sub` text without the author team's
sign-off — those fields are the algorithm itself, transcribed from Figure
3 of the source manuscript. Two nodes (`hand_forearm_note`,
`evidence_note`) use `tone: "note"` — a dashed-border aside, reached only
by a dashed "info" edge, the same pattern this atlas uses for background
information that isn't part of the main decision sequence.
